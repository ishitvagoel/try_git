01 · Setup

Get Git ready in eight moves

Install once, configure your identity, and you’ll never wonder why commits say “unknown” again.

1

Install

macOS: brew install git · Windows: Git for Windows · Linux: sudo apt install git

git --version
2

Who you are

Every commit stores author name + email. Set them globally once.

git config --global user.name "Ada Lovelace" git config --global user.email "ada@example.com"
3

Sensible defaults

Default branch name, better diffs, and a readable log alias.

git config --global init.defaultBranch main git config --global pull.rebase false git config --global alias.lg "log --oneline --graph --decorate -20"
4

First repo

Turn any folder into a repository, or clone an existing one.

git init # or git clone https://github.com/org/repo.git
5

Know your scopes

Config resolves --system → --global → --local; the nearest wins. Override identity per repo without touching global.

git config --list --show-origin git config --local user.email "work@company.com"
6

Two identities, one machine

includeIf loads a different config by directory — work email inside ~/work/, personal everywhere else.

# ~/.gitconfig [includeIf "gitdir:~/work/"] path = ~/.gitconfig-work
7

Credentials & signing

Tokens never go in remote URLs — use gh auth setup-git or a credential manager. SSH signing makes your history verifiable.

gh auth setup-git git config --global gpg.format ssh git config --global user.signingkey ~/.ssh/id_ed25519.pub git config --global commit.gpgsign true
8

Safety & hygiene

Prune dead branches, see the base in conflicts, record resolutions once and reuse them forever. Team hooks live in the repo via core.hooksPath; personal ignores in core.excludesFile.

git config --global fetch.prune true git config --global push.default current git config --global push.autoSetupRemote true git config --global merge.conflictStyle zdiff3 git config --global rerere.enabled true git config --global rerere.autoupdate true

Verify: git --version (this guide assumes Git ≥ 2.40 — zdiff3 needs 2.35, push.autoSetupRemote needs 2.37) then git config --list --show-origin | head — you should see your name, email, and defaults.

03 · Internals

Three areas, three object types

Git is a content-addressed snapshot store with movable labels. Once that clicks, every command is just moving data or pointers.

01

Commits are snapshots, not diffs

Each commit points at a full tree of your project. Unchanged files reuse the same blob hashes — that’s why snapshots stay cheap.

02

A branch is a 41-byte pointer

Creating feature writes a tiny file containing a commit hash. Branching is fast because nothing is copied.

03

HEAD says where you are

HEAD usually points at a branch name. Detached HEAD means it points straight at a commit — fine for looking, risky for new work.

blob

Raw file bytes. No filename. Same content → same hash everywhere.

tree

Directory listing: names → blob/tree hashes. Rebuilds the filesystem shape.

commit

Metadata + pointer to a root tree + parent commit(s). History is a DAG.

ref

Human name for a hash: branches, tags, remotes. Labels you move around.

Pro tip: git cat-file -t <hash> and git cat-file -p <hash> peek under the hood.

A commit names a tree; the tree names blobs (and nested trees). Filenames live in trees — not inside blobs.

06 · Workflows

Repeatable paths for real teams

Same verbs, different choreography — pick the shape that matches how your team ships.

Feature branch + PR

Isolate work, open a reviewable change, merge when green.

  1. 1git switch -c feature/x
  2. 2commit small, purposeful slices
  3. 3git push -u origin HEAD
  4. 4open PR → review → merge
git switch main && git pull git switch -c feature/login git add -p && git commit git push -u origin HEAD

Hotfix on main

Tiny, urgent patch with a clear message and fast follow-up.

  1. 1branch from the broken release
  2. 2one focused commit
  3. 3ship, then back-port if needed
git switch -c hotfix/null-check # fix, test git commit -am "fix: guard null user id" git push -u origin HEAD

Update your branch

Bring main into your branch. Personal branch? Rebase — clean and linear. Shared branch? Merge — never rewrite what others built on.

  1. 1git fetch origin
  2. 2merge or rebase onto latest main
  3. 3resolve, test, push
git fetch origin git rebase origin/main # or: git merge origin/main

Fork → PR → stay in sync

Your fork is origin; the real repo is upstream. Rebase onto upstream, publish with a lease.

  1. 1git remote add upstream …
  2. 2git fetch upstream && git rebase upstream/main
  3. 3git push --force-with-lease origin HEAD
git remote add upstream https://github.com/org/repo.git git fetch upstream git switch feature/x git rebase upstream/main git push --force-with-lease origin HEAD

Clean PR before review

wip / fix typo noise? Tag repairs with --fixup and let autosquash fold them into the commit they belong to.

  1. 1git commit --fixup abc1234
  2. 2git rebase -i --autosquash origin/main
  3. 3git push --force-with-lease
git commit --fixup abc1234 GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash origin/main git push --force-with-lease

07 · Rebasing

Rebasing, properly

Rebase replays your commits onto a new base — same content, brand-new objects, brand-new SHAs. Every benefit and every hazard follows from that one fact.

1

Update onto latest main

Working tree must be clean first — commit, stash, or rely on --autostash. Then replay onto the new tip: history stays linear. Conflicts return per replayed commit, so expect round 2, 3 … Re-run tests after every resolution, not only at the end.

git fetch origin git rebase origin/main # daily habit once configured: git pull --rebase --autostash
2

Interactive tidy-up

The todo list rewrites history on purpose: pick keep · reword message · squash/fixup meld into previous · drop delete · edit stop to amend. exec runs tests per commit.

git rebase -i origin/main # reorder lines, change verbs, save & close
3

Review round-trips

Reviewer asked for changes inside commit 2? Record a fixup and autosquash it in. Turn it on permanently with rebase.autoSquash true.

git commit --fixup abc1234 git rebase -i --autosquash origin/main git push --force-with-lease
4

Conflicts during rebase

Same drill as a merge — with one inversion: --theirs is the commit being replayed, --ours is the base you’re building on. Three exits: continue, skip (drop current commit), abort (undo all).

# resolve markers, then: git add <file> git rebase --continue # or: git rebase --skip / --abort
5

Surgery with --onto

Transplant a range: replay the commits after hotstart onto a new base. Use it to salvage work branched from the wrong place.

git rebase --onto main hotstart feature # rescue two commits from a doomed branch: git rebase --onto new-base a1b2c3d^ branch
6

Undo a finished rebase

The rewritten commits aren’t gone — ORIG_HEAD marks where you were, and reflog lists every move HEAD made.

git reset --hard ORIG_HEAD # or: git reflog git reset --hard HEAD@{4}
01

The golden rule

Never rebase commits other people have built on. Your branch, your rewrite; shared branch, merge instead. If a rewrite touches anything public, announce it first and hand teammates the refresh recipe from section 09.

02

Rebase onto, don’t merge down

git merge origin/main on a long-lived feature adds a merge commit every sync; after five syncs the PR is unreadable. git rebase origin/main keeps “my work sits on top of main” — reviewers and git log stay sane.

03

Merges need special handling

Rebasing a branch that contains merge commits flattens them. Use git rebase --rebase-merges to rebuild the topology — or simply merge for that branch. Both are fine; silent flattening is not.

08 · Conflicts

When Git can’t decide for you

A conflict means two edits touched the same lines. You choose the final truth, then tell Git you’re done.

markers in the file — zdiff3 style

<<<<<<< HEAD your version on the current branch ||||||| base what both sides started from ======= incoming version from the other side >>>>>>> feature/login

1. See what’s conflicted

List unmerged paths and open them.

git status git diff

2. Edit out the markers

Keep the correct code. Delete <<< / === / >>> lines.

3. Mark resolved & continue

Stage the file, then continue the merge or rebase.

git add path/to/file git merge --continue # or: git rebase --continue

Abort if needed

Bail out cleanly when the merge isn’t worth finishing yet.

git merge --abort git rebase --abort

Upgrade your view

zdiff3 inserts the shared base between the two sides so you see why they diverged. rerere records each resolution and replays it automatically when the same conflict returns on a later commit.

git config --global merge.conflictStyle zdiff3 git config --global rerere.enabled true git config --global rerere.autoupdate true

Triage before editing

Not every conflict shows markers. UU both modified · AA both added · DU/UD one side deleted · AU/UA one side added · rename/rename forces one new name.

git status --short git diff --name-only --diff-filter=U

Whole-file decisions

When one side should simply win, skip line surgery — this discards the other side entirely. Prefer git restore (Git 2.23+) over overloaded checkout. Always put -- before the path. In a merge: ours = your branch. In a rebase: inverted — theirs = the commit being replayed.

git restore --ours -- path/file.py # merge: keep your side git restore --theirs -- path/file.py # merge: take incoming git add -- path/file.py

Delete/modify & add/add

These have no markers — git status names them. Accept the delete with git rm, the change with git add. Add/add carries both files with in-file markers; resolve like content.

git status # "deleted by us: app/old.py" + your edits git rm app/old.py # accept delete git add app/old.py # or: keep your version

Tools for the hard ones

git mergetool walks every conflicted file in a real 3-way editor (meld, KDiff3, VS Code, difftastic). Binary files: pick a side, regenerate, then mark them unmergeable so Git stops trying to line-merge them.

git config --global merge.tool meld git mergetool # once per pattern: echo "*.png binary" >> .gitattributes
✓

Finish the operation you started

Every conflicted state has its own verb: merge → git add -A then git commit (or merge --continue) · rebase → git add then rebase --continue, once per stopped commit · cherry-pick → cherry-pick --continue · stash pop → resolve in place; changes are already applied, drop the entry when happy. Never mix verbs: merge --continue mid-rebase just errors.

!

Prove it’s really over

Before continuing, scan for forgotten markers and half-resolved files: git diff --check flags leftover <<<<<<<, and git status must be free of “both modified”. Run the tests — resolving is not the same as working.

09 · Push after rebase

Merging & pushing after a rewrite

Rebase gave your commits new SHAs; the remote still points at the old ones. The rejection below is not a bug — it is Git noticing the mismatch on your behalf.

the rejection, verbatim

$ git push To github.com:org/repo.git ! [rejected] feature/x -> feature/x (non-fast-forward) error: failed to push some refs to 'github.com:org/repo.git' hint: Updates were rejected because the tip of your current branch is behind hint: its remote counterpart. If you want to integrate the remote changes, hint: use 'git pull' before pushing again.

why it happens

old main ── A ── B ── C' ← what the remote still has (pre-rebase) ╲ new main ── D ── A' ── B' ── C' ← what you rebased to (same work, new SHAs) plain push can only add commits after the remote tip. The remote's C' is not an ancestor of your history → non-fast-forward. And no: git pull now would merge the old commits back in.

Publish a rewrite safely

--force-with-lease compares the remote tip to your local remote-tracking ref (usually origin/feature/x). A background git fetch can update that ref and silently weaken the check. Prefer the explicit form for anything sensitive. Bare -f on a shared branch is how work disappears. Protected branches are the real organizational control.

git fetch origin git push --force-with-lease origin HEAD # strongest: pin the SHA you expect to overwrite git push --force-with-lease=refs/heads/feature/x:$(git rev-parse origin/feature/x) origin HEAD # Git 2.30+ also: --force-if-includes

Teammate: refresh after a rewrite

Once the branch owner announces the rebase, everyone resets their local copy onto the new history — your old local commits stay reachable via reflog.

git fetch origin git switch feature/x git reset --hard origin/feature/x

If the force-push went wrong

Nothing is instantly gone: the pre-rewrite tip sits in your local reflog, and GitHub’s branch compare / PR timeline still know the old SHAs. Recreate, then coordinate before touching remotes again.

git reflog # find the old tip, e.g. 9f2c1ab: git branch rescue 9f2c1ab git push origin rescue

Landing: merge commit

Create a merge commit keeps the exact review topology — branch shape forever in history. Pick it when “what happened during this PR” matters (large features, audit trails).

Landing: squash

Squash and merge collapses the PR into one commit on main — the usual default for linear history. Rebase onto latest main first so CI tests the merged result, not a guess.

Landing: rebase & merge

Rebase and merge replays every PR commit directly onto main, no merge commit. Clean, but loses PR grouping metadata and needs a conflict-free replay — squash is usually the sharper tool.

Protected branches: no rewrites

Force-push to main is blocked by design on sane remotes — that’s a feature, not friction. Rewrite personal branches; change public history only with team coordination (or a revert, section 10).

# after merge, sweep up: git fetch --prune git branch -d feature/x git push origin --delete feature/x

10 · Rescue

When Git surprises you

Twelve scenarios everyone eventually hits. Symptom, cause, fix — and what prevents it next time. None of these mean you “broke Git”; they mean history has edges.

1

Detached HEAD

You checked out a commit or a PR ref, then committed — that work belongs to no branch. Save it in one move, or leave without it.

git switch -c keep/my-work # leaving without keeping: git switch main
2

Commit “lost” to reset or a bad rebase

Reflog is a diary of every position HEAD held. Find the entry, then move back to it; ORIG_HEAD is the one-step shortcut.

git reflog git reset --hard HEAD@{7} # right after the scary op: git reset --hard ORIG_HEAD
3

Dropped a stash you needed

Dropped stashes often remain as unreachable commits until garbage collection prunes them — not a 30-day promise. Act immediately, avoid git gc, and inspect the patch before applying one.

git fsck --unreachable | grep commit git stash apply <found-sha>
4

Amend a commit already pushed

Your branch, your rewrite: fix it locally, publish with a lease. Announce it if anyone else pulled the branch.

git commit --amend git push --force-with-lease
5

Undo a merge that’s already on main

Public history: revert, don’t rewrite. -m 1 keeps the mainline parent (the side the merge landed on). Gotcha — re-merging the old branch won’t re-apply until you revert the revert or rebase it fresh.

git revert -m 1 <merge-sha>
6

Wrong author email across recent commits

Identity comes from the committing machine — set it per scope (section 01). Repair a range by amending author into each replayed commit.

git rebase -i &lt;base&gt; \ --exec "git commit --amend --reset-author --no-edit"
7

Committed a secret

Rotate first — rewriting history does not erase forks, CI logs, or caches. Never pushed: amend/reset locally. Already published: revoke, freeze the repo, rewrite with git filter-repo, force-push deliberately, then have collaborators re-clone. See GitHub’s sensitive-data removal guide.

# never pushed — drop the leak from the last commit: git reset HEAD~1 -- secrets.env git commit --amend --no-edit # already published — after rotation + freeze: git filter-repo --invert-paths --path secrets.env
8

A huge binary snuck into history

Track big binaries with LFS before they’re committed. Already committed? size filters rewrite history — same coordination rules as any rewrite.

git lfs track "*.psd" # then commit .gitattributes
9

Repository feels corrupted

git fsck names the problem; a healthy remote is the fastest repair — re-clone and reapply unpushed work from reflog.

git fsck --full # then: fresh clone + git format-patch if needed
10

Cherry-pick a merge commit

A merge has two parents — pick must be told which one is the mainline, same rule as revert -m 1.

git cherry-pick -m 1 <merge-sha>
11

Hunt the commit that broke it

Bisect binary-searches history; with a test script it runs unattended from bad back to first-bad.

git bisect start HEAD v1.2 git bisect run npm test
12

Try a scary rebase without leaving your seat

Worktrees are extra checkouts sharing one object store — experiment there, delete when done, main working copy untouched.

git worktree add ../try-rebase feature/x
